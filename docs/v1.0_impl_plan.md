## 2. Corrections and additions to the specifications

Each item is a binding change. The `Spec` column names the section to amend.

### 2.1 Day arithmetic is inconsistent — fixed

**Spec:** `domain-spec.md` §6.2, §6.3, §6.5, §10.

The worked example computes `window_days` by date subtraction — 1 Jan → 20 Jan
is *19* days, 20 Jan → 5 Feb is *16*. That makes count windows **half-open**:
`[open_on, close_on)`. The opening count's date belongs to the window it opens;
the closing count's date belongs to the *next* window. Fine, and it partitions
time cleanly.

But the same example then computes window 2's overlap with January as **11
days** and still claims **100% coverage** — 19 + 11 = 30 of 31. Both cannot be
true. The error is that `[A, B]` is inclusive of `B` (§9.1) while the window
maths is half-open, so the two must be reconciled before subtracting.

**Binding rule.** Convert the requested period to half-open `[A, B+1)` and do all
day arithmetic there:

```
window_days   = greatest(close_on - open_on, 1)
overlap_days  = greatest(0, least(close_on, B_eff + 1) - greatest(open_on, A))
period_days   = (B_eff - A) + 1
```

**The worked example of §10 is therefore wrong and must be reprinted:**

| | Spec says | Correct |
|---|---|---|
| Window 2 overlap | 11 days | **12 days** (20–31 Jan inclusive) |
| Window 2 allocated | 2,131.25 | **2,325.00** (3,100 × 12/16) |
| `goods_sold_at_cost` | 5,431.25 | **5,625.00** |
| `revenue_est` | 6,517.50 | **6,750.00** |
| `gross_profit_est` | 1,086.25 | **1,125.00** |
| Coverage | 100% | 100% ✓ (19 + 12 = 31) |

This corrected example is fixture `050_allocation.sql` and is the single most
important test in the suite.

### 2.2 The period end is not clamped to today — fixed

**Spec:** `domain-spec.md` §6.5, §7.1.

"This month", selected on the 3rd, yields `B` = the 31st. Nineteen days that
have not happened yet are then counted as unsettled, so a perfectly well-kept
shop reads *"Low — these figures are largely unsettled"* for most of every month.

**Binding rule.** Everywhere a period is evaluated, use
`B_eff = least(B, store_today())`. Coverage, freshness, the unsettled-tail
message and the day counts of §2.1 all use `B_eff`. The period label shown to
the user still reads the requested range, with the effective end noted when it
differs: *"1–31 August (settled to 3 August)"*.

### 2.3 The category-scope trap — mitigated (D-B)

**Spec:** new subsection under `domain-spec.md` §3.2, and §1.4 as a fifth
limitation.

A category is a basket; a delivery is one product in it. Asked *"what was left
before this delivery?"* while holding a milk crate, a user naturally answers for
the milk. The system reads it as the whole Dairy shelf and books the rest — the
cheese still physically present — as sold at full markup. The following count
then shows stock rising unexplained, flagged as an anomaly, but the false profit
is already in a closed month's report.

Three mitigations, all binding:

**a. The category carries a contents hint.** New column
`article_category.description text` — *"lait, fromage, yaourt, beurre"* — seeded
for each category and editable in settings.

**b. The question names the whole shelf and lists it.**

> **Tout le rayon Produits laitiers** — lait, fromage, yaourt, beurre.
> Pas seulement ce que vous venez d'acheter.
> Combien restait-il, au prix d'achat ?

**c. A plausibility check before save.** A function
`check_count_plausibility(p_category uuid, p_as_of date, p_value numeric)`
returns a verdict the form acts on:

| Verdict | Condition | Message |
|---|---|---|
| `exceeds_bound` | `value > expected_on_hand(...)` | more stock than could possibly be there — a purchase is missing, or the value is wrong |
| `high_outflow` | ≥ 2 settled windows exist and implied outflow per day > 3 × the category's trailing-90-day average | an unusually large drop for the days elapsed |
| `suspicious_drop` | no history yet, `value < 0.25 × bound`, and `days_since_last_count < 7` | counted much lower than expected after only a few days |
| `ok` | otherwise | — |

A non-`ok` verdict shows a blocking confirm (*"Vous avez saisi 50, mais Produits
laitiers devrait contenir environ 1 000. Est-ce correct ?"*) with **Corriger** as
the primary action. It never prevents saving — the user may be right.

These are heuristics, and the plan says so plainly. They catch the common
mistake at the only moment it is still cheap to fix.

### 2.4 Backdated purchases — count made optional (D-C)

**Spec:** `domain-spec.md` §3.2A, §8.1; `architecture-spec.md` §2.3, §2.5.

`purchase.prior_count_id` becomes **nullable**. The rule, enforced in
`record_purchase` rather than as a table constraint (it is a cross-row
condition):

- Purchase is the category's **newest event** → the embedded count is
  **required**, exactly as specified today.
- Purchase lands **at or behind** the category's last count → the count is
  **omitted**. The purchase is recorded as inflow inside whichever existing
  window contains it. The form explains: *"Cet achat est antérieur au dernier
  inventaire de ce rayon ; aucun comptage ne sera enregistré."*

To make that rule unbypassable, **`authenticated` gets no `INSERT` grant on
`purchase`.** Every creation goes through the RPC. `UPDATE` and `DELETE` remain
direct and audited.

### 2.5 Anyone on the internet can read the books — fixed

**Spec:** `architecture-spec.md` §4.2.

`create policy authed on purchase for all to authenticated using (true)` combined
with Supabase's default-open email signup means any stranger who registers
becomes `authenticated` and gains full read/write on the store's finances. This
is the most serious defect in either document.

Two independent defences, both required:

1. **Public signup disabled** in the project's Auth settings. The single user is
   created by the owner from the dashboard.
2. **Policies check an allowlist, not merely authentication:**

```sql
create table app_user (
  user_id uuid primary key,           -- auth.users.id
  label   text not null,
  active  boolean not null default true
);

create function is_app_user() returns boolean
language sql stable security definer set search_path = public, pg_temp as $$
  select exists (select 1 from app_user where user_id = auth.uid() and active)
$$;

create policy app_user_all on purchase for all
  to authenticated using (is_app_user()) with check (is_app_user());
```

Applied to every business table. `anon` receives no grants anywhere, and
`revoke execute on all functions in schema public from anon, public` is the last
statement of the grants migration.

### 2.6 `current_date` in CHECK constraints, and the timezone — fixed

**Spec:** `architecture-spec.md` §2.3.

Two problems in `check (occurred_on <= current_date)`:

- **It is a non-immutable expression in a CHECK.** Postgres accepts it at DDL
  time, but the constraint is re-validated on restore, so a `pg_dump` taken today
  can fail to load tomorrow — the worst possible failure mode for the one
  artefact that protects the store's history.
- **`current_date` is UTC.** The shop is UTC+1. Between 23:00 and midnight local,
  the client's "today" is a day the server considers the future, and the insert
  is rejected with a nonsense error.

**Binding rule.** Add `app_settings.timezone text not null default
'Africa/Casablanca'` and:

```sql
create function store_today() returns date
language sql stable as $$
  select (now() at time zone (select timezone from app_settings where id = 1))::date
$$;
```

Every future-date guard becomes a `BEFORE INSERT OR UPDATE` trigger raising a
named exception, not a CHECK. `takings` gets the guard too — it is missing there
today (`architecture-spec.md` §2.3).

### 2.7 Window boundaries are rank-exclusive at both ends — clarified

**Spec:** `domain-spec.md` §6.2.

The spec writes `tₖ < event_order ≤ tₖ₊₁`, which reads as including the closing
event. The SQL in `architecture-spec.md` §3.2 correctly uses
`evt_rank > open_rank and evt_rank < close_rank`. The SQL is right — the event at
`close_rank` *is* the closing count. Amend the domain wording to the strict form:

```
window k contains exactly the events with  open_rank < evt_rank < close_rank
```

The date-based phrasing must go; only ranks are normative.

### 2.8 Purchase and its count can disagree — constrained

**Spec:** `architecture-spec.md` §2.5.

Nothing enforces that a purchase and its `prior_count_id` share a category or a
date, yet `v_stock_event` reads the category from the count and the ordering
anchor from the purchase. A mismatch silently corrupts the timeline. Add a
constraint trigger on `purchase` asserting, when `prior_count_id is not null`:

- `stock_count.source = 'purchase'`
- `stock_count.category_id = purchase.category_id`
- `stock_count.occurred_on = purchase.occurred_on`

Plus the existing `unique` on `prior_count_id`, and the `AFTER DELETE` cascade
already specified.

### 2.9 `markup_at` can return NULL — fixed

**Spec:** `architecture-spec.md` §3.3.

A window opening before the category's first `effective_from` — reachable by
backdating — returns no row, and `NULL × goods_sold` silently produces `NULL`
revenue that propagates through the whole chain. Add a fallback to the *earliest*
rate:

```sql
coalesce(
  (select markup_pct from markup_rate
    where category_id = p_category and effective_from <= p_date
    order by effective_from desc limit 1),
  (select markup_pct from markup_rate
    where category_id = p_category
    order by effective_from asc limit 1)
)
```

If a category somehow has no rate at all, the window is emitted as an anomaly of
kind `no_markup` rather than contributing a NULL.

### 2.10 Anomalies: two kinds, and they are not settled days

**Spec:** `domain-spec.md` §6.2, §6.5.

The spec names one anomaly. There are two, with different causes and different
fixes:

| Kind | Condition | Means |
|---|---|---|
| `negative_outflow` | `outflow < 0` | the closing count exceeds opening + purchases — a mistyped count, a missing purchase, or a wrong date |
| `losses_exceed_outflow` | `outflow >= 0` and `goods_sold < 0` | declared losses exceed everything that left the shelf — a double-entered or overstated loss |
| `no_markup` | §2.9 | a category with no markup row |

And the omission that matters: an excluded window's days **must not count as
settled**. Otherwise a period full of anomalies reports 100% coverage while
contributing no profit — precisely inverted. Binding: `settled_days` sums only
non-anomalous windows.

### 2.11 Overall coverage is undefined

**Spec:** `domain-spec.md` §6.5.

Per-category coverage is defined; "overall" is used but never computed.

```
overall_coverage_pct = Σ_c settled_days_c / (n_categories × period_days) × 100
```

over categories **active at any point in the period**. A never-counted category
contributes 0 settled days and is named in `categories_never_counted` — it
should drag the number down, because it genuinely is unsettled.

### 2.12 Retries can double-post — idempotency added

**Spec:** `architecture-spec.md` §4.1, §5.3.

§5.3 promises writes are "idempotent on retry"; nothing implements it. On a flaky
phone connection a retried `record_purchase` posts the purchase twice — and a
duplicated purchase inflates outflow, which the model reports as profit.

```sql
create table write_request (
  request_id uuid primary key,
  rpc        text not null,
  result     jsonb not null,
  at         timestamptz not null default now()
);
```

`record_purchase` and `record_count_sweep` take `p_request_id uuid not null`,
generated once per form submission (not per attempt) and returned from the cache
on a repeat. TanStack Query retries then become safe by construction.

### 2.13 There is no way to start using the system — onboarding added

**Spec:** new `domain-spec.md` §3.5.

On day one the shop is full of stock and the database is empty. Every window
needs an opening count, and nothing in either spec creates the first one.

Add `app_settings.onboarded_at timestamptz`. Until it is set, the app opens on a
mandatory **opening sweep**: every active category, one value each, at buying
price, dated today, written as standalone counts in one transaction — the §8.3
sweep screen with different copy. The dashboard is not reachable until it
completes. Categories may be deactivated during the sweep, so the owner is not
forced to invent a number for shelves they do not stock.

### 2.14 Rounding

**Spec:** new `domain-spec.md` §9.5.

Allocation produces fractions. Rule: carry full `numeric` precision through the
entire chain, round to 2 decimals **once**, at the point of emission into the
`report_period` JSON — and derive every total as **the sum of its already-rounded
components**, so that the category table on screen always adds up to the KPI
above it. A visible sum that is off by 0.01 destroys more trust than the
precision is worth.

### 2.15 Smaller items

| # | Item | Fix |
|---|---|---|
| a | `loss_nature()` returns `'shrinkage_placeholder'`, not a value of its own return type — the function as printed does not compile | Separate enum `loss_nature_t as enum ('shrinkage','owner_draw')`, per Q7 |
| b | Two purchases of one category on one day: the second count must include the first delivery | The form shows the expected on-hand figure beside the input; §2.3's guard covers the error case |
| c | Losses sort among same-date events by `created_at`, i.e. by typing order | Accepted — deterministic, and it never splits a count/purchase pair (proved by fixture `030_event_order.sql`) |
| d | `report_period` is `security invoker` but has no fixed search path | `set search_path = public, pg_temp` on every function |
| e | `stock_count` permits duplicate rows for one category, date and source | `unique (category_id, occurred_on, source)` where `source = 'standalone'`, partial index |
| f | RPC grants | `report_period`, `report_trend`, `record_purchase`, `record_count_sweep`, `check_count_plausibility`, `expected_on_hand` → `authenticated` only |

mistake meant deleting the record and re-entering it. Flagged there, deferred,
and now built.

**Charges, losses and standalone counts** are ordinary PostgREST updates —
single rows, no cross-row invariant, and the audit trigger of `0005` already
records before/after, which is what §8.5 actually asks for. **Purchases go
through a new `edit_purchase` RPC**, because an edit can move a purchase across
the §3.2A boundary in *either* direction: pulled behind the category's last
count it must give up its embedded count, pushed forward it must acquire one.
No `request_id` anywhere — an edit converges on replay, where an insert would
post the money twice.

**An embedded count is not editable from the counts screen**, and migration
`0014` adds the deferred constraint trigger that makes that a database rule
rather than a UI convention. See §2.16.

**Exit:** every record type correctable in place; `edit_purchase` proven to
cross the §3.2A boundary in both directions in pgTAP; an embedded count proven
unmovable by an ordinary `UPDATE`; `npm run verify` and `npm run build` green.

### §2.16 — The purchase/count coherence guard was one-sided (found 2026-08-11)

`0004_guards.sql` protects a purchase and its embedded count with a trigger on
**`purchase`**. Nothing guarded the other side, and `authenticated` holds UPDATE
on `stock_count` (`0006`), so a single PostgREST call moved an embedded count
out from under its purchase:

```sql
update stock_count set occurred_on = '2026-01-02' where id = <embedded>;
```

Measured on the local database: it succeeded, and the pair then disagreed about
the date. `v_stock_event` takes the category from the count and the ordering
anchor from the purchase, so the delivery is ordered against one date and valued
against another — 0004's own comment calls this *"the timeline silently
corrupted rather than failing loudly."* Reachable over the API since Phase 1,
before any edit screen existed; building Phase 9 is what found it, not what
caused it.

Fixed in `0014` by a **deferred** constraint trigger on `stock_count`. Deferred
rather than immediate because `edit_purchase` must move both rows and whichever
it writes first leaves the pair transiently disagreeing; a check that runs at
COMMIT permits any transaction that ends coherent and rejects any that does not,
including a lone PostgREST update, which commits by itself.
